# WIC 고객 안내 대화창 통합 공통마스터 — VERIFIED FINAL LOCK

## 0. 완료 판정 잠금
이 문서는 모든 분야 고객 안내·추천자료·메일 문안·중간안내서·최종안내서의 유일한 공통마스터다.

- `FINAL`, `LOCK`, `통합 완료`는 문구가 아니라 검증 상태를 뜻한다.
- 과거 관련 규칙 수집 → 항목별 대조 → 본문 반영 → GitHub 재조회 → 누락 0 확인이 끝나기 전에는 완료라고 표시하지 않는다.
- 사용자가 한 번 지적한 실패 유형은 즉시 이 문서에 흡수하고 같은 오류를 다시 사용자에게 확인시키지 않는다.
- 새 규칙은 별도 고객 안내 규칙문서를 만들지 않고 이 문서에만 통합한다.
- 최신 사용자 직접 지시가 항상 최우선이다.

## 1. 규칙 우선순위
1. 사용자의 가장 최근 직접 지시·제외·허용 조건
2. 이 `UNIFIED_CUSTOMER_GUIDANCE_RULES.md`
3. 공통 고객 DB·발송이력·거래 발행사 데이터
4. 과거 분야별 지시문·대화기록·구버전 문서

## 2. 역할 경계
### 이메일 수집/검증
- 고객 발굴
- 기관/부서/이름/직책/이메일 검증
- 고객 DB 구축
- 발송표 정렬

### 고객 안내 통합
- 검증 고객의 실제 업무축 판단
- 과거 문의·견적·구매·회신 이력 확인
- 추천자료 선정
- 메일 제목·이메일 주소·필요 문안 작성
- 중간안내서/최종안내서 데이터 작성
- 발송용 최종 출력

이미 검증된 고객 이메일·이름·직책을 임의 추정·수정하지 않는다.
고객 안내는 신규 인력 탐색이나 신규 이메일 추정을 수행하지 않는다.

## 3. 고객 필드
공통 기본 필드는 다음 순서를 기준으로 한다.
- 고객번호/등록번호
- 기관
- 부서
- 이름
- 직책
- 담당업무
- 연구/사업 키워드
- 이메일
- 전화
- 검증결과
- 과거 문의/견적/구매/회신 이력
- 추가 메모

고객번호는 고객→추천자료→안내서→발송이력까지 유지한다.
입력값이 비어 있으면 추정하지 않고 공란 또는 HOLD로 둔다.

## 4. 시작점·중복·발송이력
- 고객번호 + 이름 + 이메일을 기본 중복키로 사용한다.
- 이미 발송한 고객과 보고서는 중복 차단한다.
- 사용자가 특정 고객부터 다시 작업하라고 하면 그 고객부터 시작하고 임의로 다음 고객으로 건너뛰지 않는다.
- 이전 대화창의 마지막 실제 작업지점이 지정되면 그 지점을 최우선 시작점으로 사용한다.
- 같은 고객에게 이미 제시한 동일 자료는 재추천하지 않는다.

## 5. 고객 판단 순서
1. 기관 실제 산업·사업 맥락
2. 기관의 현재 프로젝트·사업축
3. 고객 회사/기관 최신 사업·제품·연구·투자·조직 방향
4. 부서 기능
5. 실제 담당업무
6. 연구/사업 키워드
7. 과거 실제 문의·견적·구매·회신
8. 사용자 원문·추가 메모

### 금지
- 부서명 한 단어만 보고 일반 교육·관리·소프트웨어 보고서 추천
- 산업 일반론만으로 추천
- 일방 발송 이력을 실제 관심 이력보다 우선
- 고객 업무와 넓게만 겹치는 자료 추천

과거 실제 문의·구매·견적·회신은 일방 안내보다 우선한다.

### 5-A. 고객 방향 카드 / 제외축 정밀 필터 — 필수 내부 게이트
추천자료를 찾기 전에 고객마다 내부적으로 다음 6축을 고정한다.
1. 기관 산업축
2. 부서 기능축
3. 실제 담당업무축
4. 현재 연구·사업축
5. 향후 관심 방향축
6. 제외축

각 고객 카드에는 다음을 분리해 기록한다.
- 반드시 포함되어야 할 산업·기술 키워드
- 제외해야 할 비관련 산업·기술 키워드
- 담당업무에서 직접 연결되는 보고서 주제
- 담당업무와 연결되면 안 되는 보고서 주제

후보 보고서는 제목만 보지 않고 해당 상세페이지의 소개문, 목차, 핵심 세그먼트, 적용산업까지 고객 방향 카드와 대조한다.
선별은 `기관 산업 → 부서 기능 → 담당업무 → 세부 키워드 → 제외 키워드` 순서의 screen-out 필터로 수행한다.
- 제외 키워드나 연결 금지 주제에 걸리면 제목이 비슷해도 후보에서 제거한다.
- 포함 키워드가 약하고 넓은 산업 일반론만 겹치면 PASS하지 않는다.
- 제외축은 §5의 기존 판단 순서와 §6~§10의 검증을 대체하지 않고 추가 정밀 필터로 적용한다.

## 6. 추천자료 기본 3종
1. 핵심 맞춤 자료
2. 같은 기술/산업축의 유사 확장 자료
3. 기관 맥락에 직접 연결되는 안전 공통 자료

- 검증 가능한 후보를 다시 탐색해 3종 구성을 우선하되, 직접성·거래 발행사·상세페이지 검증 조건을 충족하지 못하면 억지로 채우지 않고 고객 작업을 HOLD한다.
- 같은 고객 안에서 동일·유사 보고서 중복 금지.
- 여러 고객에게 동일한 3종 세트 반복 금지.
- 기본 3종은 서로 다른 거래 발행사로 구성한다. 동일 발행사 중복은 금지한다.
- 동일 발행사 외에는 직접성·상세페이지 검증·최신 발행일 순으로 회피구조를 적용한다.
- 3종을 서로 다른 거래 발행사로 구성할 수 없으면 억지로 동일 발행사를 반복하지 말고 HOLD한다.

## 8. 선택 우선순위
1. 고객 직접성
2. 실제 상세페이지 검증
3. 최신 발행일
4. 발행사 분산
5. 재사용·중복 위험

최신이라는 이유만으로 직접성이 약한 자료를 올리지 않는다.
- 기본 추천 자료유형은 해외 시장보고서를 우선한다.
- 보고서 제목에 특정 지역·국가명이 포함된 지역 한정 타이틀은 기본 추천 후보에서 제외한다.
- 예: `North America`, `Asia Pacific`, `Europe`, `China`, `U.S.` 등 지역·국가 한정 제목은 사용자가 지역 보고서를 직접 요청한 경우에만 허용한다.
- 지역이 목차·세그먼트에 포함되는 것은 허용하되, 보고서 제목 자체가 특정 지역·국가 한정이면 제외한다.
- 공학도서·기술도서는 고객이 도서를 직접 요청했거나, 동일 주제의 검증 가능한 해외 시장보고서가 없고 기초원리·설계·공정 등 기술심화 자료가 고객 목적에 더 직접적인 경우에만 보조 후보로 사용한다.
- 국내 보고서는 사용자가 국내 자료를 명시적으로 요청한 경우에만 별도 분리하며, 일반 고객 안내 추천에서는 우선 후보로 사용하지 않는다.

## 9. 보고서 상세페이지 원문 전용 규칙 — 최상위 잠금
고객 안내용 보고서 데이터는 **해당 발행사의 실제 보고서 상세페이지에 현재 표시된 내용만** 사용한다.

허용:
- 실제 영문 제목
- 공식 한글 제목이 페이지에 있는 경우 그 제목
- 발행사
- 페이지 수
- 정가/라이선스 가격
- 발행일
- PDF 표시
- 같은 상세페이지의 Overview / Highlights / Segmentation / Table of Contents 등 공개 내용

금지:
- 검색결과 요약으로 값 확정
- 모델 지식으로 보충
- 다른 리셀러/사이트 값 혼합
- 임의 한글 번역을 공식 제목처럼 표시
- 임의 가격·페이지·발행일·목차 생성
- 보고서 페이지에 없는 설명을 보고서 내용처럼 표시
- 다른 보고서 목차 사용

페이지에 없는 값은 공란 또는 `확인 필요`로 둔다.

### 공급가격
공급가격은 발행사 페이지 원문 값이 아니라 내부 계산값이다. 사용자가 공급가격 계산을 명시적으로 요구하거나 별도 내부 가격규칙을 호출한 경우에만 계산한다. 그 외에는 공란/확인 필요.

## 10. 보고서 검증 게이트
각 자료마다 다음을 통과해야 한다.
- 실제 발행사 상세페이지 존재
- 출력 영문 제목 = 상세페이지 제목
- 발행사 일치
- 링크 정상
- 다른 보고서로 리디렉션되지 않음
- 발행일/페이지/가격은 페이지 표시값만 사용
- 공개 콘텐츠/목차는 같은 보고서 페이지에서 확인
- 최종안내서 목차는 발행사 상세페이지의 실제 Table of Contents 영역에서 상위목차와 그 바로 아래 하위목차 2단계만 사용한다.
- 하하위·하하하위는 제외하되, 상위·직접 하위 항목은 목차 시작부터 마지막 항목까지 자르거나 요약하지 않는다.
- Summary, Insights, Segmentation, Report Scope 등 TOC 밖의 영역을 목차로 재구성하면 FAIL이다.

하나라도 불명확하면 PASS 금지.

## 11. CUSTOMER_LINK_SANITIZE_GATE
고객에게 보이는 URL은 발행사 원문 상세페이지의 순수 URL이어야 한다.

제거/금지:
utm_source, utm_medium, utm_campaign, utm_term, utm_content, fbclid, gclid, mc_cid, mc_eid, _ga, _gl, chatgpt.com 관련 문자열, 검색엔진/리디렉션 중간 URL.

`?utm_source=chatgpt.com` 등 검색 흔적이 고객용 출력에 남으면 FAIL.

## 12. 고객별 최종 출력 시작 순서 — 절대 고정
실제 고객 작업 결과는 반드시 다음 두 줄로 시작한다.

`메일 제목: [해외시장자료 안내] {기관} {이름}님`
`이메일 주소: {검증된 실제 이메일}`

- 사용자가 다른 제목 형식을 직접 지정하면 최신 지시 적용.
- 이메일 추정 금지.

## 13. 안내서 직접 붙여넣기 순서 — 절대 고정
추천자료 1 → 2 → 3 순으로 아래 블록 반복.

### 추천자료 N
1. 영문 제목
2. 한글 제목
3. 도서정보 전체 형식
4. 자세한 내용의 링크
5. 중간안내서용 공식 공개 콘텐츠 또는 최종안내서용 실제 목차

### 도서정보 원본 형식
`◇ 발행사: {발행사} ({페이지} Pages)    ◇ 정가: {정가}`
`◇ 발행일: {발행일} -PDF-    ◆ 공급가격: {공급가격}`

- `◇`, `◆`, `-PDF-`, 통화기호 등 원본 기호 유지.
- 상세페이지에 없는 값 임의 생성 금지.
- 사용자가 데이터만 원하면 새 표 대신 위 순서의 순수 텍스트 블록 제공.
- 최종안내서 목차는 공개된 상위+직접 하위 2단계를 처음부터 마지막까지 포함하며 임의 축약하지 않는다.
- 목차 다음에는 상세페이지의 시장규모·CAGR·전망 등 수치가 있는 공개 원문을 짧게 한글 번역한 `보고서 정보`를 표시한다.

## 14. 한글 제목
- 상세페이지에 공식 한글 제목이 있으면 그대로 사용.
- 공식 한글 제목이 없고 사용자가 `페이지에 있는 내용만`을 요구하면 임의 번역 금지.

## 22. PASS / HOLD / FAIL
### PASS
- 시작점 정확
- 고객/자료 중복 없음
- 고객 실제 축과 직접 매칭
- 거래 발행사 기준 적용
- 실제 상세페이지 검증
- 임의 데이터 없음
- URL 정화 완료
- 안내서 순서/목차/복사 규칙 준수
- 고객번호 기존값 승계 및 중복 없음

### HOLD
- 직접성 높은 추천 3종을 거래 발행사·상세페이지 검증 조건까지 충족해 확보하지 못함
- 상세페이지 핵심값 미확인
- 링크 안정성 미확인
- 원본 렌더 검증 불가
- 분야 접두어 또는 기존 마지막 고객번호를 실제 DB에서 확인하지 못함

※ 거래 발행사 여부가 불명인 개별 자료는 §7에 따라 후보에서 즉시 제외한다. 그 자료 자체를 HOLD 후보로 남기지 않는다. 제외 후에도 검증 가능한 직접성 높은 3종을 구성하지 못할 때만 고객 작업을 HOLD한다.

### FAIL
- 시작 고객 임의 변경
- 무관 자료 추천
- 외부/제외 발행사 사용
- 제목-링크 불일치
- 임의 데이터 생성
- 다른 보고서 목차 사용
- 추적 URL 노출
- 안내서 순서/원본 구조 훼손
- 검증하지 않고 완료/PASS 선언
- 기존 고객번호를 새 번호로 재발급하거나 다른 고객에게 재사용

## 24. 통합 완전성 검증 프로토콜 — 필수
중앙마스터를 수정하거나 과거 규칙을 통합할 때 반드시 아래를 수행한다.

1. 관련 과거 대화기록/지시문/보완문서를 실제 내용으로 검색한다.
2. 규칙을 기능별로 분해한다: 고객판단 / 고객번호 / 추천 / 발행사 / 보고서 검증 / 메일 / 안내서 / 목차 / 링크 / 가격 / 출력 / 복사 / 스팸회피 / PASS-HOLD-FAIL.
3. 규칙 원장에 최소 `규칙 ID / 작업군 / 출처 / 원래 규칙 / 최신 여부 / GitHub 반영 여부 / 반영 위치 / 충돌 규칙 / 최종 규칙 / PASS-HOLD-FAIL`을 기록한다.
4. 각 과거 규칙에 대해 중앙마스터 대응 항목이 있는지 대조한다.
5. `반영 / 충돌로 대체 / 현재 지시로 폐기 / 미반영` 상태를 판정한다.
6. 미반영은 중앙마스터에 추가한다.
7. GitHub 파일을 실제로 수정하고 Commit SHA를 확인한다.
8. 수정 직후 GitHub에서 같은 파일을 다시 FETCH한다.
9. 원래 규칙 원장과 재조회 파일을 다시 항목별로 역대조한다.
10. 원본 규칙 수 / 최종 적용 규칙 수 / GitHub 반영 규칙 수 / 누락 규칙 수 / 충돌 미해결 수 / 잘못 삭제된 기존 규칙 수 / 최신 지적사항 미반영 수를 확인한다.
11. `누락 0 / 충돌 미해결 0 / 잘못 삭제 0 / 최신 지적 미반영 0`일 때만 통합 검증 완료로 판정한다.

GitHub 쓰기 성공 응답만으로 완료 처리하지 않는다. **재조회와 역검증이 필수다.**
과거 `FINAL`, `COMPLETE`, `LOCK`, `통합 완료` 표시는 증거로 사용하지 않는다.

## 26. 분야별 영구 고객번호 — 기존번호 우선 잠금
- 고객번호는 분야별 영구번호이며 한 번 부여하면 변경·삭제·재사용·재배정하지 않는다.
- 고객 안내는 이메일 수집/기존 DB에서 넘어온 고객번호를 그대로 승계하고 새 번호를 다시 발급하지 않는다.
- 신규 입력에 번호가 없으면 먼저 기존 DB에서 `기관+이름`, `기관+이메일`, `이름+이메일`을 대조해 기존번호를 추적한다.
- 진짜 신규 고객이며 해당 분야 번호체계와 마지막 번호가 실제 자료로 확인된 경우에만 다음 미사용 번호를 부여한다.
- 분야 접두어를 추정하여 만들지 않는다.
- 현재 확인된 번호체계는 다음과 같이 관리한다.
  - 반도체: `SEM-###` — 실제 고객 안내 원문에서 확인됨.
  - 탄소·복합재: 기존 고객 안내 원문에 `C-###` 계열이 실제 사용 중이므로 기존 `C-###`를 보존한다. 기존 고객을 `CAR-###`로 일괄 변경하지 않는다.
  - 로봇: `ROB-###` — 기존 중앙 고객업무 규칙의 확정 계열을 승계한다.
  - 방산: `DEF-###` — 기존 중앙 고객업무 규칙의 확정 계열을 승계한다.
  - 조선/해양: `SHP-###` — 기존 중앙 고객업무 규칙의 확정 계열을 승계한다.
  - 배터리: `BAT-###` — 기존 중앙 고객업무 규칙의 확정 계열을 승계한다.
  - 인공지능 및 그 밖의 분야: 기존 확정 번호체계가 실제 자료에서 확인되기 전에는 접두어를 임의 생성하지 않고 HOLD한다.
- 서로 다른 분야 고객은 섞지 않는다. 한 고객이 복수 분야와 관련되어도 원본 고객번호를 유지하고 분야 태그로 연결한다.

## 30. 41번 → 42번 직접 운영 — 최신 우선 잠금
- 기본 고객 운영 흐름은 `41번 이메일 수집/검증 → 42번 고객 안내`다.
- 41번에서 검증된 고객정보·고객 고유번호·확인된 과거 이력을 42번이 그대로 승계하며, 42번에서 다시 신규 번호를 발급하거나 같은 검증을 처음부터 반복하지 않는다.
- 42번은 고객 컨택 판단 기능을 내부에 포함한다. 따라서 현재 업무축 판단, 과거 문의·견적·구매·회신·발송 이력 대조, PASS/HOLD/FAIL 판정, 추천자료 선정, 안내서 데이터 작성, 메일 제목·본문 및 필요한 후속 문안까지 42번에서 연속 처리한다.
- 7번 고객 컨택 판단은 기본 필수 경유 단계가 아니다. 복잡한 후속 컨택 전략, 특수 연락 분기, 별도 정밀 판단이 필요한 경우에만 보조로 사용한다.
- 과거 문서나 진행기록에 `41 → 7 → 42`가 기본 흐름으로 적혀 있으면 이 최신 규칙으로 대체한다.
- 7번을 보조로 사용하는 경우에도 동일 고객 고유번호와 42번의 검증·발송 이력을 그대로 이어받으며 중복 생성하지 않는다.
